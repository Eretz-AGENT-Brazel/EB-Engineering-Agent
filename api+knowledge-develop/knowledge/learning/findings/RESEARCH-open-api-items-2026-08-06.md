## PsCutObjects — all ten cut types, plus PsVertexChamfer / PsEdgeChamfer / PsCutPlane / PsOutlet

**Verdict:** `partly-available`

PsCutObjects (Bentley.ProStructures.Modification.Edit) is a pure CREATOR class: every SetAs* member returns Void, so failure is silent — only Apply() returns Int32 and GetNewObjectId()/GetModifyIndex() report what was produced. All ten cut types exist in the dump exactly as listed, and every payload class (PsVertexChamfer, PsEdgeChamfer, PsCutPlane, PsOutlet, PsPolygon) is fully reflected. The blocker is semantic, not structural: the manual documents these only as dialog fields (B.12 3D-Modifications, B.13 Plate Editor, E.9.12–E.9.16), and the PICTURES that name the six edge-processing layouts and the three chamfer layouts were not captured in the extracted text — so the EdgeLayout enum-to-picture mapping and the Var1/Var2 role per layout are partly inferred and must be proved empirically. There is NO member on PsCutObjects for a rounded-cut radius or a miter gap; if those numbers reach the cut at all it is via SetOffset, which is unproven.

**Pitfalls found:**

- EVERY SetAs* RETURNS Void. A wrong ObjectId, a degenerate polygon, a plane that misses the part, a zero Depth — all produce no exception and no message. Only Apply() returns anything, and even its success value is undocumented. Never report a cut as done on the strength of the call returning.
- CREATOR vs READER. PsCutObjects CREATES. PsEditModification READS and DELETES (DeleteAllPolycuts, DeleteCutPlane(handle), DeletePlateBreakEdge(), CutPlaneCount, OutletCount...). Never look for a SetAs* on PsEditModification and never look for a Count on PsCutObjects — neither exists.
- VICTIM vs CUTTER. SetObjectId names the part being modified. Every SetAs*Id(Int64 Object) names the OTHER object. Swapping them cuts the wrong member, silently.
- SetToDefaults() IS NOT OPTIONAL. Without it the instance carries whatever the previous cut left (offset, subbody type, automatic flag) and the cut lands somewhere plausible but wrong.
- SetAsRoundedCutId HAS NO RADIUS PARAMETER, yet manual p.207 says the arc radius is essential ('this radius can either be entered as absolute value or as many times the maximum diameter of the first shape'). Likewise SetAsMiterCutId has no Gap parameter despite the dialog's 'Gap A gap of this thickness is kept between the shapes at mitered cuts'. SetOffset is the only candidate carrier for both and this is UNPROVEN. Do not ship rounded cuts until measured.
- PsEdgeChamfer HAS NO FROM-EDGE / TO-EDGE MEMBERS. The manual's 'Selected Edge Here, you indicate from which edge to which edge the processing has to be made' has no API counterpart; the only selector present is 'P Int32 FlangeIndex'. Expect all-around processing (which the manual says is what happens when start == end) and plan around it.
- THE EdgeLayout MAPPING IS PARTLY INFERRED. The manual's p.233 figure naming the six layouts is an IMAGE and is not in the extracted text. kFacet (chamfer, Var1+Var2) and kFold (seam, Var1=depth, Var2=height) are well supported by the Var1/Var2 prose; kRadius / kRounded / kInverted / kNotch are inference. Also kNotch does not exist in the older PSCOMWRAPPERLib.KsEdgeLayout enum, so a V8i SS6 build may reject it.
- PsEdgeChamfer EXPOSES THREE EdgeLayout PROPERTIES: TopEdgeLayout, DownEdgeLayout and a bare EdgeLayout. Their interaction is undocumented. Set Top/Down explicitly; do not rely on the bare one.
- ONLY ONE PLATE BREAK EDGE PER PART. PsEditModification has 'P PsEdgeChamfer PlateBreakEdge' with no count, and 'M Void DeletePlateBreakEdge()' with no handle. A second SetAsPlateBreakEdgeCut on the same part probably REPLACES the first rather than adding.
- THE ENUM MEMBER IS SPELLED kCommenBody, not kCommonBody. Copy it character-for-character or you burn a compile cycle.
- SetAsBooleanCut TAKES AN Int64 OBJECT ID, not a PsToolBody. The tool solid must already exist in the model. And AutoCAD's own UNION/SUBTRACT will NOT work on ProSteel objects — manual B.12.7: 'there will be no errors, but nothing will happen!'
- POLYCUT POLYGON MUST BE CLOSED AND NON-SELF-INTERSECTING. Manual: 'be careful that the lines don't overlap in the polygon' and 'the poly-line has to be closed, even if it is used as contour'. Call Close() and checkIntersection() first — an invalid polygon is a silent no-op.

## Positioning / part numbering from code (Posnumber / Sendnumber assignment) — ProStructures V8i SS6, AutoCAD 2015 .NET API

**Verdict:** `partly-available`

Yes — position numbers CAN be assigned from code without any dialog, but NOT by running ProSteel's positioning engine. The engine class `Bentley.ProStructures.Miscellaneous.PsCreatePositioning` has ~90 `Set*` configuration methods and ~60 `Internal*` step methods but NO public `Perform/Run/Execute/Apply/Create` and NO `SetToDefaults`/`Initialize` — the only orchestrator is the modal PS_POS dialog. What IS fully available is direct per-object write: `PsObjectProperties.Posnum` / `.Sendnum` / `.Originalnum` + `writeTo(Int64)`, `PsGroupProperties.Posnum`/`.Sendnum` + `writeTo(Int64)`, and `PsAssembly.setPosnum/setSendnum/setOrigPosnum`. Equal-part detection is also exposed independently of the dialog, via `PsObjectProperties.IsEqualTo(...)`, `PsGroupProperties.IsEqualTo(...)` and `PsCompareDrawing.CheckTwoPartsAreEqual(Int64,Int64)`, and the number-string arithmetic (numeric/alpha/mixed) is exposed via `PsCreatePositioning.ConvertNum2Posnum` / `ConvertPosnum2Num` / `ComparePosnum` / `SearchLastNumber`. So the practical answer is: build your own numbering pass using ProSteel's own equality and number-format primitives, then write the numbers per object. Driving the `Internal*` chain is a possible but unproven second path, and two of its members (`InternalPositioningOptions`, `InternalDisplay*Result`) are dialog openers that must never be called. There is no documented dash-prefixed or scripting variant of PS_POS — the manual's command reference lists exactly one token, `PS_POS`.

**Pitfalls found:**

- PsCreatePositioning has NO public run method. I read all ~200 member lines (dump 71277-71557): no SetToDefaults, no Initialize, no Perform, no Apply, no Create, no Execute, no Run, no Start. Every orchestration member is Internal*. The COM twin IKs_ComPositioning (dump 52945) is identical, so there is no COM back door.
- PS_POS has no dash-prefixed or scripted variant. The manual's full command reference lists exactly one token: 'Positioning B.28 PS_POS'. No -PS_POS, no PS_POS_AUTO anywhere. PsMiscTools.SendKeyIn(String) could fire it but opens the same modal dialog. Do not burn a NETLOAD cycle guessing aliases.
- The manual contradicts itself on the section number: TOC says 'B.29 Positioning 376', the command index says 'B.28 PS_POS'. Content is at manual text lines 8948-9296.
- No SetToDefaults on PsCreatePositioning, unlike sibling PsCreatePartlist which has 'M  Void SetToDefaults()' (dump 71273). A fresh instance inherits whatever the last PS_POS dialog left behind. Set every parameter explicitly and verify with InternalRetrieveParameter, or your run silently uses yesterday's tolerances.
- SetColumnTol / SetBeamTol / SetSubGroupColumnTol / SetSubGroupBeamTol / SetAssemblyColumnTol / SetAssemblyBeamTol are ANGLES, not lengths, and they do not affect equality at all — they only pick which PREFIX a group gets. Manual: 'you enter an angle within which the shape is still considered to be vertical.' Feeding mm silently mislabels every column as 'other'. Degrees-vs-radians is not stated in either source — measure it.
- SetHolesTol is the opposite trap: it sits among the angle tolerances but is a LENGTH. Manual: 'Drill Hole Tolerance – Deviations of the drill hole axes up to the specified length are not considered for a comparison.'
- SetMinSingleVol / SetMinGroupVol are RELATIVE PERCENTAGES and only apply when SetVolCheck(true). Manual: 'as relative value to the compared volume (e.g. 0.1 percent for component parts and 0.2 percent for groups).' Passing cubic mm makes every part identical.
- HARD ORDERING RULE: singles before groups, always. Manual B.29.1 'Group Detection': 'single parts are only compared using their position number because positioning has already been carried out before.' Numbering groups first, or both in one loop, produces silently wrong group numbers with no error.
- Nearly every configuration method on PsCreatePositioning returns Void — SetColumnTol, SetHolesTol, SetLengthTol, SetWeightTol, SetStep, SetLastNumber, SetFilters, SetCompareFilter. Failure is silent. The only read-backs are InternalRetrieveParameter(out ...), GetStep(), GetLastSingle()/GetLastGroup(), and InternalControlUseSendnum(). Assert after setting, every time.
- PsObjectProperties.readFrom(id) MUST precede any write. The class is a detached property block, not a live handle. Setting Posnum on a fresh instance and calling writeTo pushes a blank block over Name, Note1, Note2, Article, Material and every display flag — data loss with an Int32 return that may still look fine.
- Near-duplicate property names. PsObjectProperties uses 'Originalnum'; PsGroupProperties uses 'OrigPosnum' for the same concept; PsVolume exposes BOTH 'Posnum' and 'PosNumber' plus 'Originalnum' and 'OriginPosNumber' side by side, undocumented. Use PsObjectProperties/PsGroupProperties, whose names match the manual's dialog labels.
- PsAssembly.setPosnum / setSendnum / setOrigPosnum return Void — total silent failure, no exception contract. The only proof is getPosnum()/getSendnum()/getOrigPosnum() straight back.

**Verdict:** `partly-available`

**Pitfalls found:**

- SetToDefaults() is not optional. PsCollisionCheck wraps the PERSISTENT PS_COLLISION dialog state — skip it and you silently inherit whatever pairings and MinVolume the last interactive run (or the last agent run) left behind, which is the classic 'why did it suddenly take 40 minutes' failure.
- CreateBodys=false makes the run unreadable. BodyCount is all you get; there is nothing left in the model to inspect, so you cannot tell WHERE the clash is. Always set it true and clean up afterwards.
- CollectObjectsFromSelection returns Void. An empty or wrongly-filtered PsSelection produces a perfectly successful-looking run with BodyCount 0. ALWAYS assert sel.ObjectCount > 0 before the call — a 0-collision result from an empty set is indistinguishable from a genuinely clean model.
- Apply() returns Int32 but §D.5.1 never defines it. Do not read it as a collision count, a body count, or a boolean. BodyCount is the documented result ('Actual/Max ... total amount of solids found'). Treat a non-zero rc as 'unknown' until measured against a model with a known single clash.
- There is NO way to fetch collision body i. ZoomToObject(Int32 index) proves an internal 0..BodyCount-1 array exists but only moves the viewport — it returns nothing and hands back no id. Every id-level result must be recovered by before/after diff or by SelectColor(CollisionBodyColor).

- The manual is explicit that the cost is quadratic: 'the required time increases with the square of the number of selected component parts ... it is often more reasonable to check only a certain junction point at a time.' On a 500+ part EB model a whole-model run with bolts enabled is not a slow operation, it is a hung session. Always box-restrict.

Bentley.ProStructures.Modeling.PsObjectGroup is a complete, self-contained group engine: the SAME class both CREATES (Initialize → setMainPart → AddSubPart → Create/CreateSubGroup/CreateAssembly) and READS/EDITS (GetGroupFrom → PartCount/getPart/getMainPart, AddMemberToGroup, RemoveMemberFromGroup, DeleteGroupFrom) — which side you are on depends entirely on whether you called Initialize() or GetGroupFrom(). It exposes aggregate weight (computeWeight), bounding dimensions (ComputeDimension) and centre of gravity (WeightCenterOfGroup), plus full nesting navigation (getMainPartOf / getTopMainPartOf / getAssemblyMainPartOf / getAllPartsOf / getAllSubGroupPartsOf). It has NO rename method and NO parts-list data beyond Groupname — for Posnum/Name/Note1/Note2/Weight/Length/Width/Height/IsSubGroup/IsAssemblyGroup you must use Bentley.ProStructures.Property.PsGroupProperties (readFrom/writeTo/RecomputeData). Export/import as a block IS in the API — Bentley.ProStructures.Drawing.PsBlock.CreateBlockFile (the WBLOCK equivalent the manual B.28.2 describes) and PsBlock.InsertBlock / PsBlockReference.Perform for re-insertion — but the BlockCenter library itself (manual D.2, PS_BLOCKCENTER, with its own database) has NO managed API in the dump apart from PsGlobalSettings.BlockCenterPath, so the library is dialog-only; the file-level block round-trip is the scriptable path.

**Pitfalls found:**

- ONE CLASS, TWO MODES. PsObjectGroup both creates and reads. Initialize() starts a NEW group; GetGroupFrom(id) loads an EXISTING one. Calling getPart/getMainPart/PartCount/Groupname without GetGroupFrom first returns stale or zero data with no error. Never reuse one instance for a create and a read in the same scope.
- GetGroupFrom returns Void. If the id belongs to no group you get silence, and the instance keeps whatever it held before. ALWAYS gate on PartCount > 0 immediately after.
- Groupname is an INDEXED property. The dump prints 'P  String Groupname' with no index because this dumper strips indexer parameters — the same artefact makes PsSelection's 'P  Int64 Object' and PsTemplate's 'P  String String' look scalar next to their Count properties. A bare g.Groupname will not compile / will throw. Use the indexer or reflection with an index argument.
- DeleteGroupFrom(Int64) is Void AND ambiguous. The manual gives two distinct buttons — 'dissolve a group' (parts kept) and 'delete all parts of the selected group from the drawing' (parts erased) — and the dump gives one method with no hint which it is. Prove it on a throwaway group by counting parts before/after before pointing it at real work.
- AddMemberToGroup / RemoveMemberFromGroup / AddSubPart / AddSubParts / setMainPart / ComputeDimension / SetToDefaults / SetInsertMatrix are ALL Void. Every membership edit in this API fails silently. Nothing is done until you re-read it.
- computeWeight returning 0.0 and ComputeDimension leaving 0/0/0 mean FAILURE, not 'this group weighs nothing'. Treat 0 as an error condition.
- Stale aggregates. PsGroupProperties.Weight/Length/Width/Height are stored values. After changing members you must call RecomputeData(id) (itself Void) or you will read and export yesterday's numbers into the parts list.
- Assemblies have no main part. getMainPart() returns 0 for a legitimate assembly and ALSO for a corrupt group whose main part was deleted (manual B.28.3 — the Check-Groups function dissolves such groups). Disambiguate with PsGroupProperties.IsAssemblyGroup before treating 0 as an error.
- setMainPart before CreateAssembly is wrong. Assemblies take Origin/XAxis/YAxis instead, because there is no main part to carry the coordinate system.
- There is no rename method on PsObjectGroup. Renaming goes through PsGroupProperties.readFrom → Name → writeTo. The name is a 30-character field in the parts-list/PPS schema; longer strings will be truncated downstream.
- NEVER use the AutoCAD BLOCK/WBLOCK/EXPLODE commands on a group. The manual B.28.2 states it twice: 'The AutoCAD standard commands for blocks cannot be used' and 'Do not use the standard AutoCAD command for this task!' Use PsBlock.CreateBlockFile / PsBlock.BlockExplode(id, KeepProperties: true) / PS_EXPLODE only.
- Export the COMPLETE group. The manual's export option is 'Complete Group — the complete group will always be exported, even if only one component part of this group was selected.' In the API nothing does that for you: call getAllPartsOf(mainPart, false, IncludeSubGroups: true) yourself, or you will ship a block missing its nested subgroups.

**Corrections to the recipe:**

- Section A, Groupname: WRONG CALL. `pi.GetValue(g, new object[] { 0 })` passes a boxed Int32 0 as an ITEM INDEX. The index is an Int64 OBJECT ID - the shipped plugin does `g.get_Groupname(qid)` where qid is the part's object id (EBAgentApi48.cs:3183). Index 0 is not an object id, so this returns empty/garbage even if the default binder widens Int32->Int64. Reflection is also unnecessary: the C# compiler exposes get_Groupname(long) directly. Replace with `string n = g.get_Groupname(anyPartId);` inside a try/catch.
- Section A/E: MISSING Initialize(). The recipe calls GetGroupFrom / getMainPartOf on a fresh PsObjectGroup with no Initialize(). Every proven call site in this codebase does `g.Initialize(); g.GetGroupFrom(id);` (EBAgentApi48.cs:3172-3174 and :3245-3247). The recipe treats Initialize() as a CREATE-only prerequisite (section D). Add it on the read path too - it costs nothing and matches the only code known to work.
- Section D: `bool ok = c.Create(); if (!ok) throw` - TRUSTS A BOOL RETURN THIS CODEBASE HAS ALREADY MEASURED LYING. EBAgentApi48.cs:3238-3240 and the v38 note at :3264 record a Create() that returned FALSE while the operation had in fact worked (the cope case). The shipped group op explicitly does NOT judge by `made`; it re-reads with a second PsObjectGroup (Initialize + GetGroupFrom + PartCount) and reports EB_ERR only when readback <= 0. As written, section D will throw on successful group creations. Replace the throw with the read-back proof.
- Section G: READER USED WHERE A WRITER IS NEEDED - this is failure mode (1). `PsCreatePositioning.GetNextGroupPosnum(true,false)` only RETURNS a string; nothing in the recipe ever assigns it to the 40 groups, so section G as written gives all 40 nothing. The write path is the one the recipe already found in section C: gp.readFrom(id) -> gp.Posnum = groupPos -> gp.writeTo(id) -> readFrom again to compare. (PsCreatePositioning also carries CalculateNextGroup / InternalDispatchNumbers, but those are undocumented in the dump - do not guess.)
- Section G: PsCompareDrawing.ComparePartsAndGroups(sel) cannot be called cold. The class has ReadTemplateFile / ReadTemplateFolder / ReadCompareDrawing(PsSelection) and SetTolerances, i.e. a template must be loaded first. Calling ComparePartsAndGroups on a bare instance proves nothing about the 40 copies. Also available and probably what is actually wanted: CheckTwoPartsAreEqual(Int64,Int64).
- Section F3: `foreach (var p in fortyPlacements) blk.AddBlockReference(...)` DISCARDS the Int64 return. That is the same sin as trusting a Void: 40 silent no-ops all look like success. Capture the id and fail on 0, and census the drawing before/after.
- Section F2: nothing verifies the insert. `int rc = br.Perform()` is captured then correctly distrusted, and `br.PartsCount` is read but never checked. If Perform is the only evidence, F2 has no evidence at all. Either drop F2 or gate it on a before/after entity census plus PartsCount > 0.
- Section F1: `PsSelection parts = blk.BlockExplode(refId, true)` - result never checked. Add `if (parts == null || parts.ObjectCount == 0) throw`. Note PsSelection.ObjectCount is a plain-looking property with the same indexed-property caveat, but ObjectCount is far more likely genuine than Object.

**Still unknown:**

- Whether DeleteGroupFrom(Int64) dissolves the group and KEEPS the parts, or erases the parts from the drawing. The manual documents these as two separate commands; the dump exposes one method. Untested — potentially destructive.
- The index domain of the indexed Groupname property. Live testing established that get_Groupname takes an index, but neither source says what the index selects (name level? nesting level? part slot?) or what the valid range is. There is no GroupnameCount in the dump.
- Whether Groupname has a setter at all, and whether setting it commits to the drawing or requires a subsequent Create()/writeTo. The dump's 'P' marker does not distinguish get-only from get/set.
- Whether PsBlock.BlockExplode's BlockId parameter is the block REFERENCE id returned by InsertBlock/AddBlockReference or a block DEFINITION id (as GetBlockIdFromBlockName returns). Same ambiguity for BlockGetObjects and SetBlockOrigin.
- Whether PsBlock.BlockExplode is the ProSteel-safe explode (equivalent to PS_EXPLODE) or a thin wrapper over AutoCAD's EXPLODE. KeepProperties=true suggests the former; the manual explicitly forbids the AutoCAD command, so this must be proven once by reading group structure back after an explode.
- Whether PsBlockReference.BlockName expects the DWG filename with or without the .dwg extension, and whether BlockPath needs a trailing separator.
- The meaning of PsBlockReference.Perform()'s Int32 return (0 = success? = parts created? = an error enum?). No enum in the dump maps to it.
- Whether PsBlockReference.SetObjectId + Perform clones an existing in-drawing reference, or whether ObjectId is an OUTPUT holding the newly created reference.
